# Team AI Enablement

> 部門內部的 AI 工作資產與採用機制。把散落在個人手上的 AI 使用經驗，收斂為可複用的共享資產，並設計讓它真的被使用的制度。

**我的角色：** 專案發起人與基礎建設負責人。負責使用者研究、資產建置（Skill Repo / Prompt Library）、制度與模板設計、跨城市推廣。制度的核准與資源分配由部門主管決定，我不參與核准與評分。

---

## ① Problem & Context（問題與背景）

我訪談了部門內 7 位跨職能同仁（RD、QA、設計、PM、業務，橫跨台北與北京兩個辦公室），以半結構式進行，聚焦三個問題：目前工作上的痛點、目前怎麼用AI、對於分享成果的看法。

訪談歸納出三項發現：

**一、工具使用已普遍，但深度落差大。**
所有受訪者都已自發使用 AI 工具，種類涵蓋多家廠商。落差出現在使用方式：同一類任務，有人已整理成可重複執行的腳本，有人則每次透過聊天視窗重新描述需求。

**二、流程成本是首要顧慮。**
受訪者對工具補貼樂見，同時過半數主動提到不希望申請與匯報流程過重。故制度本身的摩擦力必須低於它帶來的好處。

**三、共享意願高。**
對共建 Prompt Library 與 Skill Repo，受訪者普遍持開放態度，願意把自己的做法提供出來。同時也需要一個好上手的地方匯集。

另有一項環境約束：兩個辦公室可存取的工具種類不同。任何綁定特定工具的制度都無法同時適用兩地。

## ② My Role & Key Decisions（我的角色與關鍵決策）

我的任務：把「每個人各自摸索」的現況，轉為「一次沉澱、多人複用」的部門資產，並設計讓這個資產能持續被使用的機制。

**決策 1：制度不綁定特定工具**
- 面臨選擇：指定統一工具（便於議價與管理），或以用途為評估基準、不指定工具
- 我的決定：申請書以「用途、預期產出、可沉澱的資產」為評估項目，不指定工具品牌
- 理由：兩地可存取的工具不同，綁定特定工具會讓其中一地無法適用；且訪談顯示同仁已各有慣用工具，強行統一會製造遷移成本

**決策 2：模板一律壓縮到最短**
- 面臨選擇：完整的申請與回報表單，或最小可用版本
- 我的決定：申請書、月度成果書、週報記錄格式各壓到一頁以內，欄位只保留決策必需項
- 理由：訪談中「流程不要過重」是唯一被一半以上受訪者主動提及的訴求。制度的採用率取決於摩擦力高低，資訊完整度可以在彙整階段補齊

## ③ Process & Artifacts（過程與產出物）

### 使用者研究
> 7 位跨職能訪談（RD、QA、設計、PM、業務 × 兩地辦公室），以半結構式進行，聚焦三個問題：目前工作上的痛點、目前怎麼用 AI、對於分享成果的看法。

### Skill Repo 架構

採 monorepo 模式，所有 Skill 收在單一 repo，頂層以 `_模版/` 存放治理文件。

```
department-skills/
├── _模版/
│   ├── README模版.md          # 每個 Skill 的說明格式
│   └── 上傳規範.md            # 貢獻門檻與命名規則
├── skill/
│   ├── <字體檢測類 Skill>
│   ├── <格式轉換類 Skill>
│   ├── <風格分析類 Skill>
│   ├── <週期性報告類 Skill>
│   └── ...
├── archive/
└── README.md
```

> 目前累計 8 個可複用 Skill，涵蓋字體檢測、格式轉換、風格分析、週期性報告等類型。
>
> `_模版/` 是這個 Repo 的治理核心。README 模版讓所有 Skill 的說明格式統一，使用者不需為每個 Skill 重新適應閱讀方式；上傳規範則把貢獻門檻明文化，取代口頭約定。
>
> 門檻設計的出發點是：讓人找得到、讓人知道如何用。

### 治理文件
📄 [Skill 說明格式模版](./governance/skill-readme-template.md) ｜ [上傳規範](./governance/contribution-guide.md)
> 這兩份文件定義了一個 Skill 要達到什麼標準才能進入 Repo：命名規則、必要欄位、說明文件的最低要求，以及不予合併的情況。

### 範例 Skill
📁 [`examples/sample-skill/`](./examples/sample-skill/)
> 一份依照上述規範撰寫的完整 Skill（已去識別化），包含說明文件。
> 範例僅公開說明文件，工具本體為公司資產不隨附。

### 制度模板
📄 [工具申請書模板](./governance/tool-request-template.md)
> 申請書刻意壓縮至一頁以內，只保留用途、預期產出與可沉澱的資產三個欄位，不要求填寫工具品牌。
> 另有月度成果書與週報記錄格式，同樣以最小欄位設計，直接嵌入既有的週報流程，不另開新表單。

### 推廣與擴散
> 發起部門 AI 讀書會系列（規劃四場，單場 16 人以上參與），主題涵蓋工具使用、實作分享與資產貢獻。
> 讀書會同時扮演貢獻入口的角色：分享者在準備過程中會把自己的做法整理成可傳達的形式，那份整理物本身就是 Repo 的內容。

## ④ Outcome & Impact（結果與反思）

**在啟動前定義的成功指標：**

1. 基礎建設是否建成並讓部門知道如何使用（Library、Repo、模板）
2. 讀書會場次的完成度與參與人數
3. 沉澱進 Library / Repo 的可複用 Prompt / Skill 累計數量
4. 月度彙總估算的節省工時

- 三套模板推行至全部門，15位同仁穩定使用
- Skill Repo 累計 8 個可複用 Skill，5 位設計師與 PM 實際複用
- 讀書會已完成 4場，單場 16 人以上參與（參與率超過9成）
- 月度部門估算節省超過100+hr的工時

### What I'd do differently（可以做更好的地方）

**指標的品質仍不夠好。** 第四項「月度彙總估算節省工時」由同仁自填，這在方法上不可靠：沒有基準線、沒有統一的估算方式、且填寫者有高估的動機。若重來，我會改為追蹤可客觀觀察的行為指標，例如 Repo 的複用次數、同一個 Skill 被多少人 fork，取代請人估算一個無法驗證的數字。
